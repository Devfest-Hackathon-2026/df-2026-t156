# 2026-11-08 通信と時計の実時間比較

公開revision11の「後半で時計/NPCが遅くなり、連打後にロールバック」という本人レビューを受けたローカル測定。旧runtimeは変更前の6モジュールを別ディレクトリへコピーして起動、新runtimeはprotocol2。すべて通常180秒、実WebSocket入力20Hz、15〜120秒に攻撃IDを毎回更新し採掘のfireも保持、以降60秒は攻撃を停止した。開始位置からの素振りを主に測り、対人命中の操作再現や実Chromeの描画負荷とは区別する。

下記の初回8人比較と1Mbps比較は、未消費上限**2枚**の時点での測定。最終採用の**3枚**による測定は末尾に分け、初回Chrome記録の最大未ACK2枚も当時の結果として保持する。

合計93.62%減。この条件では旧版も時計停止は再現しなかった。旧版は受信帯域が足りればサーバーtick自体は短く、連打だけで無制限に伸びる攻撃/pose/event配列は観測していない。新方式はプレイヤー数だけsnapshotを生成する処理を1回へ集約し、低頻度状態・移動・イベントを分けている。

## 1人＋通常BOT2体、下り1Mbps

TCPプロキシが上流の全データを受け取り、下流を125,000bytes/秒へ制限。サーバーのsocket.bufferedAmountが0でも、実際の受信者の前にはキューがある条件。65秒には双方のNodeプロセスを1.2秒停止させる設定。

旧版では古いsnapshotと一緒にpingも下りキューへたまり、heartbeatが応答を待ち切れず30秒で接続を終了。人間がいなくなった部屋はBOTも外れ、world.time=30秒で待機した。プロキシの残データはその後も流れるため、受信側はさらに古い時計/NPCを見る。これは旧版の180秒完走ではなく、失敗条件の記録である。新方式はUnityが実際に消費したseqを入力で返し、未消費の2フレームで送信を止めるため、TCP/プロキシの手前だけ見たbackpressureに依存しない。

新の1.2秒停止では約0.25秒分だけ物理を補完し、残り0.95秒は時計・入力期限・移動予算へ反映。時計の遅れが停止後に残らず、BOTと試合結果も進んだ。本人の公開回線やブラウザFPSを同じ条件で測ったものではなく、本人の現象の原因をこれ一つと断定する結果ではない。

## 近接を保つ未消費3枚への調整

実WebSocket2接続と現行OrbitSocket.jslibを使用し、送受信それぞれ30/60/40/50msの遅延をFIFOで加えた。入力ACKは50msごと、受信消費と相手の補間を約60Hzで実行。画面上の補間された相手を照準し、横切る相手へのクリック、50ms間隔40連打、650ms停止後の単発、その後450msの再生有無を確認した。これは実WebGL描画・音の測定ではない。対人命中後の反復確認では位置をfixtureへ整列し、ノックバック軌道の比較とは分けた。

|同じ公称60〜120ms RTTのjitter条件|2枚|最終3枚|
|---|---:|---:|
|連打中の消費更新頻度|10.14Hz|15.86Hz|
|到着時に視点履歴250msを超えたクリック|4/42|0/42|
|最大未消費枚数|2|3|
|横切りへのクリック→命中通知|138ms|186ms|
|停止後の単発→swing通知|110ms|169ms|
|単発通知後に遅れて届いた古いswing|0|0|

新条件は50〜80ms RTTのjitterでも横切り命中122ms、単発106ms、期限切れ0/42。両接続で同じ命中event idを受けた。数値は一回ごとのスケジューラ差を含み、すべての通知時間が短くなるという比較ではない。上限3により消費ACK待ちの間も最新位置を送りやすくし、届いた通常クリックを視点履歴の期限で失う例を減らした。射程3m、視点履歴250ms、受信後キュー250msは拡張していない。

`melee.test.js`に、受信時は履歴240msで有効な命中が次tickで捨てられないことと、400ms止まった古いクリックを破棄した後も新しい単発が成立する確認を追加。`melee-stream.test.js`と`stream.test.js`を合わせた13件が通過した。検証用遅延もTCPの順序を保つFIFOで実装し、タイマーだけで同時刻の配送順が入れ替わる試験側の不備を除いた。
